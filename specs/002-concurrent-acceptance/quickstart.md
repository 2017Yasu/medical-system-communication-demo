# Quickstart: S2 同時受付の動作確認

本機能が端から端まで動くことを確認する手順。仕様は [spec.md](spec.md)、設計判断は [research.md](research.md)、
画面と API は [contracts/](contracts/)、ポリシーと版の変化は [data-model.md](data-model.md) を参照。
講演・展示での操作手順そのものは `docs/06-demo-procedures.md`（本機能で作成）に書き、本書はその手順が成り立つことの確認に絞る。

## 前提

S1 の [quickstart.md](../001-lab-order-workflow/quickstart.md)「前提」「1. ビルドと起動」と同じ。
UI を変えたら JAR（または Docker イメージ）を作り直してから E2E を実行する（CLAUDE.md）。

## 1. 自動テスト

```bash
# サーバー：S2-1〜S2-3 の結合テスト（S2-2 の同時確定は既定 100 回、S2-1・S2-3 は既定 20 回）
cd server && mvn verify -Dit.test=S2ScenarioIT

# 回数を変える（SC-002 の記録は 100 回、SC-003 は 20 回）
cd server && mvn verify -Dit.test=S2ScenarioIT -Ds2.repeat=100

# デモ制御 API（labSendsIfMatch の部分更新・初期化で既定値に戻ること）を含む全テスト
cd server && mvn verify

# UI の単体テスト（diffRows・diffVersions・AcceptDraft の If-Match・準備の順序・エラー文言）
cd ui && npm test

# E2E：S2 の 4 ウィンドウ操作（起動済みのサーバーに対して実行）
cd ui && npx playwright test tests/e2e/s2-concurrent.spec.ts

# E2E：画面からの同時確定を 100 回（SC-002。数分かかる）
cd ui && S2_REPEAT=100 npx playwright test tests/e2e/s2-concurrent.spec.ts -g "同時に確定"

# E2E：S1 の回帰（受付の 2 段階化の影響。D-27）
cd ui && npx playwright test
```

**期待結果**: すべて成功。S2ScenarioIT は、S2-2 の各回でちょうど 1 つの PATCH が 200、もう 1 つが 412 になり、
作業の担当者が 200 を受けた側であることを確かめる（data-model.md §2）。

## 2. 手で確認する（4 つのウィンドウ）

`http://localhost:8080/` の入口の「S2 同時受付で開くウィンドウ」から、次の 4 つを別々のウィンドウで開いて並べる。

| ウィンドウ | URL |
|---|---|
| デモ制御パネル | `/control` |
| 検体検査システム（技師 A） | `/lis?tech=tech-a` |
| 検体検査システム（技師 B） | `/lis?tech=tech-b` |
| 通信モニタ | `/monitor` |

### 2.1 S2-1（ルール無し → 上書き）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S2-1 の準備」 | 10 秒以内に「S2-1 の準備ができました」（SC-005）。設定の表示が「任意」「付けない」。技師 A・B の見出しが「版の確認：付けない（デモ設定）」。両方の一覧に「依頼済み・採取済」の依頼。通信モニタに初期化・ポリシーの変更・医師 X の POST・看護師 D の POST |
| 2 | 技師 A で「受付」、続けて技師 B で「受付」 | 両方に確認欄が開き、同じ版（例：版 2）が表示される。通信モニタに技師 A・技師 B の `GET Task` |
| 3 | 技師 A で「受付を確定」 | 技師 A の確認欄が閉じ、行が点滅して「状態：依頼済み → 受付済み」「担当：検査部 → 技師 A」。技師 B の一覧も点滅して同じ変化を示すが、**技師 B の確認欄は開いたまま**。通信モニタに「PATCH Task/…（If-Match なし）」→ 200 |
| 4 | 技師 B で「受付を確定」 | 成功する（エラーは出ない）。技師 A の一覧が点滅して「担当：技師 A → 技師 B」（D-28）。通信モニタに 2 つ目の「PATCH（If-Match なし）」→ 200 |
| 5 | 通信モニタで作業の版の履歴を開く | 3 つの版が並び、最新の版で担当のセルが強調され、「この版を作った通信」に「技師 B」 |

### 2.2 S2-2（版の確認あり → 後発は 412）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S2-2 の準備」 | 設定が「必須」「付ける」。見出しが「版の確認：付ける」。一覧が準備後の状態に戻る |
| 2 | 技師 A・技師 B の順に「受付」 | 両方の確認欄に同じ版 |
| 3 | 技師 A で「受付を確定」 | 成功。通信モニタに「PATCH（If-Match: W/"n"）」→ 200 |
| 4 | 技師 B で「受付を確定」 | 技師 B のエラー欄に「この依頼は既に 技師 A が受付済みです（412 Precondition Failed）」。一覧は「受付済み・担当 技師 A」。自動でやり直さない。通信モニタに同じ `If-Match: W/"n"` の PATCH → 「412 他の利用者が先に更新済み」（失敗の表示）と、技師 B の取り直しの GET |
| 5 | 版の履歴 | 技師 B による版は無い（最新の版は技師 A が作った版） |

### 2.3 S2-3（必須化 → 版の確認が無い更新は 400）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S2-3 の準備」 | 設定が「必須」「付けない」 |
| 2 | 技師 A で「受付」→「受付を確定」 | エラー欄に「版の確認（If-Match）が無い更新はサーバーが受け付けません（400 Bad Request）」。作業は「依頼済み・採取済」のまま。通信モニタに「PATCH（If-Match なし）」→「400 版の確認が必要」 |
| 3 | 制御パネルでサーバーの版の確認を「任意」に変え、技師 A で再び「受付」→「受付を確定」 | 成功する（US3 シナリオ 3）。通信モニタに「ポリシーの変更」 |

### 2.4 初期化・その他

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 確認欄を開いたまま制御パネルで「初期化」 | 4 つのウィンドウが初期状態に戻り、確認欄が閉じる。設定が既定（必須・付ける） |
| 2 | 準備ボタンを続けて 2 回押す | 2 回目は 1 回目の完了まで押せない。完了後に押すと、結果は 1 回押した場合と同じ |
| 3 | 技師 A で「受付」→「取りやめ」 | 確認欄が閉じ、PATCH は送られない |
| 4 | ステージビューで S1 の講演モードを最後まで進める | S1 は従来どおり動く。ステップ 4 で技師 A の「受付」→「受付を確定」が自動で行われ、通信モニタに GET と PATCH が出る |
| 5 | `docker run --network none` で起動したイメージで 2.1〜2.3 | 同じ結果（SC-006） |

各手順の「期待結果」が画面と一致すること、解説込みで 5 分以内に収まること（SC-001）を確かめる。結果は validation-results.md に記録する。
