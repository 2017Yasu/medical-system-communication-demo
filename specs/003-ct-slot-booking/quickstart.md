# Quickstart: S3 予約枠の取り合いの動作確認

本機能が端から端まで動くことを確認する手順。仕様は [spec.md](spec.md)、設計判断は [research.md](research.md)、
画面と API は [contracts/](contracts/)、リソース・ポリシー・状態の変化は [data-model.md](data-model.md) を参照。
講演・展示での操作手順そのものは `docs/06-demo-procedures.md`（本機能で S3 の節を追加）に書き、本書はその手順が成り立つことの確認に絞る。

## 前提

S1 の [quickstart.md](../001-lab-order-workflow/quickstart.md)「前提」「1. ビルドと起動」と同じ。
UI を変えたら JAR（または Docker イメージ）を作り直してから E2E を実行する（CLAUDE.md）。

## 1. 自動テスト

```bash
# サーバー：単体テスト（期限切れの保持・予約枠の生成・検索パラメータ・ポリシーの検証）
cd server && mvn test -Dtest='SlotHoldExpiryTest,SlotSeedGeneratorTest,SearchMatcherTest'

# サーバー：S3-1〜S3-3 の結合テスト（S3-2 の同時の仮押さえは既定 100 回、S3-1・S3-3 は既定 20 回）
cd server && mvn verify -Dit.test=S3ScenarioIT

# 回数を変える
cd server && mvn verify -Dit.test=S3ScenarioIT -Ds3.repeat=100

# S1・S2 の回帰を含む全テスト（FR-025）
cd server && mvn verify

# UI の単体テスト（CT 予約の組み立て・BookingDraft・エラー文言・シーケンス図・版の履歴・準備）
cd ui && npm test && npm run typecheck

# E2E：S3 の 5 ウィンドウ操作（起動済みのサーバーに対して実行）
cd ui && npx playwright test tests/e2e/s3-slot-booking.spec.ts

# E2E：画面からの同時の仮押さえを 100 回（SC-002。数分かかる）
cd ui && S3_REPEAT=100 npx playwright test tests/e2e/s3-slot-booking.spec.ts -g "同時に仮押さえ"

# E2E：S1・S2 の回帰
cd ui && npx playwright test
```

**期待結果**: すべて成功。S3ScenarioIT は、S3-2 の各回でちょうど 1 つの仮押さえが 200、もう 1 つが 412 になり、
確定後の 10:00 の枠の予約が 1 件だけであることを確かめる（data-model.md §3.2）。

## 2. 手で確認する（5 つのウィンドウ）

`http://localhost:8080/` の入口の「S3 予約枠の取り合いで開くウィンドウ」から、次の 5 つを別々のウィンドウで開いて並べる。

| ウィンドウ | URL |
|---|---|
| デモ制御パネル | `/control` |
| 電子カルテ CT 予約（医師 X） | `/ehr/ct?doctor=dr-x` |
| 電子カルテ CT 予約（医師 Y） | `/ehr/ct?doctor=dr-y` |
| 放射線部門システム | `/ris` |
| 通信モニタ | `/monitor` |

### 2.1 S3-1（直接予約 → 二重予約）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S3-1 の準備」 | 10 秒以内に「S3-1 の準備ができました」（SC-006）。予約方式が「直接予約する」。医師 X・医師 Y の見出しが「予約方式：直接予約する（デモ設定）」。枠の一覧は翌日 9:00〜11:30 の 6 枠（9:00・11:00 は予約済み、ほかは空き） |
| 2 | 医師 X・医師 Y の順に 10:00 の「枠を選ぶ」 | 両方に予約欄が開き、同じ版（版 1）。通信モニタに医師 X・医師 Y の `GET Slot/ct1-1000` |
| 3 | 医師 X で「予約を確定する」 | 「予約しました（…デモ 太郎）」。10:00 の枠は「空き」のまま。放射線部門システムの 10:00 の行にデモ 太郎、「枠は空きのまま」。通信モニタに「POST Transaction（一括登録）」→ 200、中身の表に Slot の行が無い |
| 4 | 医師 Y で「予約を確定する」 | 成功（警告なし）。放射線部門システムの 10:00 の行にデモ 太郎・デモ 花子、「同じ枠に予約が 2 件あります」と強調。予約・作業の一覧に 2 件 |
| 5 | 通信モニタで `Slot/ct1-1000` の版の履歴を開く | 版 1（空き）だけ |

### 2.2 S3-2（仮押さえ → 確定、後発は 412）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S3-2 の準備」 | 予約方式が「仮押さえを使う」。見出しが「予約方式：仮押さえを使う（期限 30 秒）」。予約は初期データの 2 件だけ |
| 2 | 医師 X・医師 Y の順に 10:00 の「枠を選ぶ」 | 両方の予約欄に版 1 |
| 3 | 医師 X で「仮押さえする」 | 医師 X に残り時間。全ウィンドウの 10:00 が「仮押さえ中（医師 X）」。通信モニタに「PUT Slot/ct1-1000（If-Match: W/"1"）」→ 200 と ping |
| 4 | 医師 Y で「仮押さえする」 | 医師 Y のエラー欄に「この枠は 医師 X が仮押さえ中です。別の枠を選んでください（412 Precondition Failed）」。予約欄が閉じる。自動でやり直さない。通信モニタに同じ `If-Match: W/"1"` の PUT →「412 他の利用者が先に更新済み」と、医師 Y の取り直しの GET |
| 5 | 医師 X で「確定する」 | 「予約しました（…デモ 太郎）」。10:00 が「予約済み」。放射線部門システムに予約と作業（依頼済み・予約済み）。通信モニタに「POST Transaction（一括登録・枠の版の確認あり）」→ 200、中身の表に `PUT Slot/ct1-1000（ifMatch: W/"2"）` → 200 と 3 つの POST → 201 |
| 6 | `Slot/ct1-1000` の版の履歴 | 版 1 空き → 版 2 仮押さえ中（医師 X）→ 版 3 予約済み。医師 Y による版は無い |

### 2.3 S3-3（期限切れ → 確定は全体が 412）

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 制御パネルで「S3-3 の準備」 | 予約方式が「仮押さえを使う」、期限 30 秒 |
| 2 | 医師 X で 10:00 の「枠を選ぶ」→「仮押さえする」 | 残り時間が 30 秒から減る |
| 3 | 確定せずに待つ | 30 秒後から 2 秒以内に、全ウィンドウの 10:00 が「空き」（SC-005）。医師 X の予約欄は開いたまま、残り時間は「期限切れ（サーバーの処理を待っています）」。通信モニタに「FHIR サーバー：仮押さえの期限切れ Slot/ct1-1000（仮押さえ中 → 空き、版 2 → 3）」と ping |
| 4 | 医師 X で「確定する」 | エラー欄に「仮押さえの期限が切れました。枠を選び直してください（412 Precondition Failed）」。10:00 は空きのまま。放射線部門システムに予約が増えない。通信モニタの中身の表で entry 0（PUT Slot）が失敗、ほかは「取り消し」、「一括送信の全体が取り消されました」 |
| 5 | `Slot/ct1-1000` の版の履歴 | 版 1 空き → 版 2 仮押さえ中（医師 X）→ 版 3 空き（作った通信：FHIR サーバー（仮押さえの期限切れ）） |
| 6 | 制御パネルで期限を 60 に変えてから、医師 Y で仮押さえする | 医師 Y の残り時間が 60 秒から始まる。通信モニタに「ポリシーの変更」 |

### 2.4 初期化・その他

| # | 操作 | 期待結果 |
|---|---|---|
| 1 | 医師 X が仮押さえ中に制御パネルで「初期化」 | 全ウィンドウが初期状態に戻り、予約欄が閉じる。30 秒経っても通信モニタに期限切れの記録が出ない（FR-004） |
| 2 | 医師 X で仮押さえ → 「取りやめる」 | 10:00 が「空き」に戻る（版が上がる）。通信モニタに `PUT Slot/ct1-1000（If-Match: W/"2"）` → 200 |
| 3 | 制御パネルで期限に 5 を入れて「変更」 | 送られず「10〜300 秒で指定してください」 |
| 4 | ステージビューで S1 の講演モードを最後まで進める、S2 の準備を押して S2-2 を操作する | S1・S2 は従来どおり。医師 X の検体検査の依頼一覧に CT の依頼が混ざらない（S3 の後に初期化しないで開いた場合も） |
| 5 | `docker run --network none` で起動したイメージで 2.1〜2.3 | 同じ結果（SC-007） |
| 6 | コンテナのタイムゾーンが UTC のまま、日本時間の 0 時をまたいで初期化 | 枠の日付が日本時間の翌日になる |

## 3. 手順書との突き合わせ

`docs/06-demo-procedures.md` の S3 の節を、開発に関わっていない人が読んで 2.1〜2.3 を実演し（SC-009、20 分以内）、
各手順の「期待結果」が画面と一致すること、解説込みで 10 分以内に収まること（SC-001）を確かめる。結果は validation-results.md に記録する。
